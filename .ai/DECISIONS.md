# AccessGuard — Decision Log

| Date | Decision | Rationale | Alternatives Considered |
|---|---|---|---|
| 2026-11-21 | Scan credentials are managed with `requireVerifiedEmail(request, { permission: MANAGE_SETTINGS })` | The hand-rolled check (`customRole.permissions.includes(...)` on a JSON string + admin/owner role test) was weaker than the shared RBAC guard and skipped the built-in permission matrix. Credential material is admin-level, not member-level (`run_scans`). | `run_scans` permission (members could then read session cookies); keeping the manual check (diverges from `src/lib/rbac.ts` and misses custom roles). |
| 2026-11-21 | All secrets in a scan-auth config are encrypted at rest (cookie values, sensitive headers, login script, login credentials) | The first implementation encrypted cookies and some headers only; the login script and the login credentials were stored in clear text even though they carry session tokens. AES-256-GCM via `@/lib/crypto` was already the house mechanism. | Plaintext + DB-level encryption only (a DB dump would leak credentials); refusing to store login scripts at all (feature gap). |
| 2026-11-21 | The login script and the credentials are never returned by the API; reads mask cookie values and sensitive headers | The first implementation returned the script unless `scriptConfig` was present — a leak of executable code and embedded credentials. Masking keeps the UI usable without exposing secrets. | Returning secrets to admins (defeats at-rest encryption); no masking (the UI cannot show what is configured). |
| 2026-11-21 | The login script runs in the page context as an async IIFE, with the credentials exposed as `window.__accessguardAuth` | The first implementation filled `USERNAME_PLACEHOLDER`/`PASSWORD_PLACEHOLDER` — the login could never succeed. The script must use DOM/fetch APIs (Playwright APIs do not exist inside the page), so the credentials are injected as a page global instead of being embedded in the stored script. | Playwright-driven script DSL (new DSL to design and document); server-side `fetch` login (cannot drive DOM-only logins). |
| 2026-11-21 | Every active config of a project is merged (cookies + headers), first login script wins | Only using the first config made additional configs silently ineffective. | First config only (simpler, but silently drops credentials); one config per project enforced (schema change, breaks existing rows). |
| 2026-11-21 | `projectId` is validated by the Zod schema at the top level of the create body | It was read from the raw unparsed body via `as any`, so the API contract and the OpenAPI spec disagreed. | Keep the raw read (works, but the spec lied about the contract). |
| 2026-11-21 | The public onboarding endpoints get a real rate limit (5/min per client, shared bucket) | Both routes claimed "rate-limited" in their comments but had none, while each request spawns a real browser scan — a compute-abuse vector. The shared bucket stops a client from doubling its allowance by switching endpoints. | Allowlisting them as public without a limit (unbounded scan cost); a separate bucket per endpoint (double the allowance). |
| 2026-11-21 | The audit-whitelist test scans only audit writes (`createAuditLog` / `auditLog.create`), not every `action:` property | The blanket regex flagged `IntegrationLog.action` values (`test`, `create_issue`, `notify`) as audit actions, which would have polluted the audit taxonomy with non-audit values. | Adding non-audit values to `AUDIT_ACTIONS` (wrong taxonomy); dropping the test (loses drift detection). |
| 2026-11-21 | Two new migrations repair the chain instead of editing history | `prisma migrate deploy` failed on a fresh database: `Organization.pagesQuota` was never created by a migration, and the agency/integration/violation schema only reached local databases through `prisma db push`. Both new migrations are idempotent so fresh and existing databases converge. | `db push` in production (loses migration history); rewriting old migration files (breaks deployed databases that already applied them). |
| 2026-11-21 | `github-action/dist/**` is excluded from ESLint | The committed esbuild bundle produced 9 lint errors (require() imports, this-alias) in generated code and blocked the "lint must be 0 errors" gate. | Editing generated code (reverted by the next build); disabling rules globally (hides real issues). |
| 2026-11-21 | Dependencies were upgraded to close the published advisories (next 16.4.6, @sentry/nextjs 10.78.0, zod 4.6.7, prisma 6.19.3) plus overrides for effect/source-map-js/vite/brace-expansion/sharp | `npm audit` reported 2 critical and 8 high advisories. The gate is Critical=0 / High=0. `npm audit fix` crashes on this lockfile, so the upgrades were applied explicitly and verified with the full gate suite. | Leaving the advisories (fails the security gate); `--force` (unreviewed major bumps). |
| 2026-11-21 | This cycle is shipped as **V21** (`vol: <area> — V21: <summary>`) | The repository's definition of done mandates the `vol: <area> — V<n>: <summary>` format and the last documented volume is V20. The most recent feature commits used a `- P1:` variant instead; the DoD format wins. | Continuing the `- P1:` variant (drifts from the documented DoD); a separate V21 volume document (the work is hardening plus one feature, not a new volume). |
| 2026-11-21 | The severity + emerald tokens were retuned for **text** contrast (WCAG AA, 4.5:1) instead of adding separate "text-safe" token variants | The same tokens are 12px badge text on `bg-<severity>/10` and risk-score numbers on the card, so they need 4.5:1, not the 3:1 that fills and icons need. A second set of tokens would mean a second class vocabulary (`text-critical-text`) for five colours. The new lightness values were computed with `oklch → sRGB → WCAG` math before any CSS was written, so the result is reproducible, not eyeballed. | Keeping the vivid fills and darkening only the text classes (one-off class edits in every badge, and the risk gradient would no longer match the number next to it); a `*-text` token family (double the palette surface). |
| 2026-11-21 | The two stale Playwright specs were fixed in the specs, not in the product | The landing CTA already routes authenticated visitors to `/dashboard` (correct product behaviour) and the privacy tab copy is already correct — the tab click simply landed before React hydration attached the Radix handler. Changing product behaviour to satisfy a wrong expectation would have shipped a worse product. | Making the landing CTA always go to `/auth/login` (kicks signed-in users out of their session); forcing the settings tab open via a URL parameter (new product surface for a test). |
