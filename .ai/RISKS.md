# AccessGuard — Risk Register

Updated: 2026-11-22

| # | Risk | Probability | Impact | Rating | Mitigation | Status |
|---|---|---|---|---|---|---|
| 1 | A login script stored per organization is arbitrary JavaScript executed against the scan target | Medium | High | 🟠 HIGH | Only admins (`manage_settings`) can create one; scripts are encrypted at rest and never returned by the API; the scanner runs them in the browser sandbox of the target page, not on the server | Accepted (documented in `docs/engineering/SCAN_AUTHENTICATION.md`) |
| 2 | A login script runs once per page in crawl mode, making authenticated crawls slow | High | Low | 🟡 MEDIUM | Documented limit; cookie/header auth stays cheap; reduce `crawlConfig.maxPages` for script-auth projects | Open |
| 3 | Dependency upgrades to next 16.4.6 / prisma 6.19.3 could change runtime behaviour | Medium | Medium | 🟡 MEDIUM | Full gate suite re-run after the upgrade (typecheck, lint, 407 vitest, next build, prisma validate + generate, zero-drift migration check) | Mitigated |
| 4 | `prisma db push` on the dev database drifts from the migration chain again | Medium | Medium | 🟡 MEDIUM | `prisma migrate deploy` is the source of truth; `migrate diff --to-schema-datamodel` reports zero drift for both the dev and a fresh database | Mitigated |
| 5 | Shared test fixtures across API route suites caused cross-file user/org collisions | High | Medium | 🟡 MEDIUM | Unique e-mail per suite plus deterministic upserts; rbac/tenant-isolation mocks now use real database rows | Mitigated |
| 6 | Public onboarding scans remain a compute-abuse vector behind a single proxy IP | Medium | Medium | 🟡 MEDIUM | 5/min per client; for a shared egress IP the limit is shared — consider a signed token or CAPTCHA if abuse appears | Open |
| 7 | No E2E coverage for the new credential API | Medium | Low | 🟢 LOW | Contract tests cover auth, permission, tenancy, encryption, masking, update and delete | Open |
| 8 | Fix verification needs a Chromium binary at request time; without it every fix is unverified and no PR can be opened | Medium | Medium | 🟡 MEDIUM | Resolution order: `PUPPETEER_EXECUTABLE_PATH` → `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` → system Chromium → Playwright browser. The Docker image ships system Chromium, CI installs the Playwright browser before the unit suite. The route fails closed with an explicit error rather than opening an unverified PR | Mitigated |
| 9 | Verification is rule-level on the remediation snippet, not a full page re-scan, so a fix can still break surrounding code | Medium | High | 🟠 HIGH | The patched file is re-parsed (syntax guard), a patch that would delete visible text is rejected, the PR is reviewed by a human before merge, and the PR summary states exactly what was verified. Full page verification needs the customer's build and stays on the roadmap | Accepted (documented in `docs/ai/FIX_VERIFICATION.md`) |
| 10 | `.vue` / `.svelte` / `.astro` files fall back to an exact text match and can miss the target | Medium | Low | 🟢 LOW | Conservative fallback: it never guesses, and a missed target leaves the fix out of the PR instead of corrupting the file | Open |
| 11 | The Docker image runs Chromium as root, so the OS sandbox is disabled for the verification browser | Medium | Medium | 🟡 MEDIUM | The verification document carries a restrictive CSP, the context aborts every HTTP request and closes every WebSocket, only markup that passed the safety checks is rendered, every run has a 15 s deadline, and the route is rate limited per user. Running the container as a non-root user (and installing the Chromium sandbox packages) is the follow-up | Mitigated |
| 12 | The element is located by content, not by a source map from the scanned URL, so a match can be ambiguous | Medium | Medium | 🟡 MEDIUM | Every identity attribute the report carries must match, the whole source tree is scanned under a byte budget, and an element found in more than one file is no longer patched at all — it ships as a review suggestion. A source-map mapping is on the roadmap | Mitigated |
| 13 | A verification request costs a Chromium launch and one axe run per fix | Medium | Low | 🟡 MEDIUM | The request is capped at 25 violations **before** the browser work, the route is rate limited per user, the browser is launched once per request and reused for the whole batch, and a global semaphore runs at most two batches at a time | Mitigated |
| 14 | The NVIDIA free-pool list still names `meta/llama-3.3-70b-instruct`, which the provider reports as end-of-life (HTTP 410 Gone since 2026-08-26) | High | Low | 🟡 MEDIUM | The router fails over on any 4xx, so the chain still completes — the cost is one wasted provider call per AI remediation when NVIDIA is in the pool. Found while trying to run the Strix pentest; replacing the entry needs a live check of the current NVIDIA catalogue (next AI volume) | Open |
| 15 | The Strix autonomous pentest cannot run: every configured provider refuses (Gemini free tier quota exhausted, NVIDIA model EOL, OpenAI credits exhausted) | High | Medium | 🟠 HIGH | The two independent human-agent reviews (QA + security, then a security re-review) covered the V23 diff instead, and `npm audit` covers the dependency surface. Strix must be re-run against the same sanitized export once a provider has quota — until then it is not evidence and is not cited as such | Open (blocked by provider quota, not by the code) |
| 16 | The first V23 hardening pass was reported as fixed while equivalent paths were still open — a closed-loop gap in how findings were verified | Medium | High | 🟠 HIGH | The re-review reproductions were re-run as a temporary suite and every one became a permanent regression test. A fix now needs the reproduction to fail before and pass after, not a claim in the state file | Mitigated |
| 17 | A repository larger than the 5 MB scan budget is never patched in place, so large customers only get review files | Medium | Low | 🟢 LOW | Accepted: a complete scan is required to prove uniqueness, and a partial scan could patch the wrong file. The source-map mapping (risk 12) is the real fix | Open |
| 18 | A fix whose element occurs more times in the file than the selected fixes is never patched (it stays a review suggestion) | Medium | Low | 🟡 MEDIUM | The fixes are matched to the occurrences in order, so the mapping to a specific occurrence is only provable when every occurrence is covered. Selecting one of two identical elements therefore stays a review suggestion instead of patching the wrong one. A source map from the scanned URL would make the mapping exact (risk 12) | Accepted |
| 19 | The image gate depends on `trivy-action` behaviour that is not obvious: the SARIF format drops the severity filter, so the exit code counts every severity | Medium | Medium | 🟡 MEDIUM | The workflow sets `limit-severities-for-sarif: true` and pins the scanner (`v0.76.2`). A future action upgrade may change the default again — the image scan has to be re-checked when the action is re-pinned | Mitigated |
| 20 | The third independent review closed the *literal* reproductions of the second review but left equivalent paths open (CSS escapes, `frame`/`frameset`, `aria-hidden`, incomplete scans, the audit retry, the occurrence mapping) | Medium | High | 🟠 HIGH | Every finding of the third review is fixed and each reproduction is now a permanent regression test. A fourth independent review verifies the fixes before the tree is called ready | Mitigated |
